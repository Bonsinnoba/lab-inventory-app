### Final V2 responsiveness and optimization protocol

**Priority:** preventing the freezes experienced in V1 is a top release requirement, ahead of cosmetic polish. Status: **NOT RUN / stable release blocked pending evidence**. Two implementation batches move sixteen hot native reads off the invoke handler through two bounded worker lanes, coalesce overlapping SyncStatus polling and bound Resource/folder rendering to 48 entries per page. Notes/Search session fencing accompanies off-thread work. Source verification and bounded installed 2.3.1 offline navigation/process sampling are recorded in WORK_LOG; large-data and two-hour acceptance remain NOT RUN. This applies across Phase 2 and Phase 3, not just to the music player or renderer. No promise of zero freezes is justified without measurement.

- **Use the installed release build on the lab PC:** include working encryption, packaged converters and normal WebView/media behavior. Record build hash, Windows/WebView version, CPU/RAM, fixture sizes and timings. Use isolated synthetic data comparable to the real lab workload and at least one larger dataset (target twice the normal volume); never stress-test by modifying V1 data.
- **Measure before optimizing:** capture renderer long tasks/event-loop stalls, interaction latency, React renders, native command durations, SQLite query/transaction/lock waits, sync-stage duration, CPU, memory and disk I/O. Include the main process, WebView processes and converter children. Collect bounded local diagnostics without passwords, tokens, document contents or audio recordings.
- **Exercise the expensive paths together:** cold/warm startup and session restoration; large Inventory/Resources lists and nested folders; search/filter/navigation with the assistant open; multiple/folder uploads; thumbnail extraction; long PDFs with zoom/pan and two viewer panels; DOCX conversion; music pause/resume/next/previous and lab-media/TTS takeover. Also exercise imports/exports, recovery operations and a large pending outbox while typing and navigating.
- **Test disconnection and recovery:** stop only the target Docker API, keep working locally, restore it and test automatic reconnect plus manual retry. Include slow/unavailable server requests, bounded lock contention, failed/cancelled transfers and rapid navigation. Timeouts/retry storms must not freeze the shell, destroy drafts or require killing the app. Missing hardware/providers remain explicitly unpassed, not simulated passes.
- **Fix demonstrated causes:** move CPU-heavy/blocking file, crypto, conversion and database work off UI/async executor threads using bounded workers; shorten transactions and inspect query plans/indexes; paginate/virtualize expensive lists; stream large bytes; bound concurrency and retries; cancel stale work; avoid unchanged refresh rerenders; release media/object URLs/listeners and converter processes. Profile each change. Do not disable encryption, authorization, digest checks, atomic outbox writes or receipt validation for speed.
- **Acceptance targets:** ordinary clicks, typing, scrolling and playback controls should respond within 200 ms at p95 under the representative workload; no unexplained main-thread/UI stall of 1 second or longer, Windows Not Responding state, deadlock, crash or forced restart. Longer jobs must show progress and leave unrelated navigation/input responsive, with safe cancellation where supported. Investigate repeated long tasks above 250 ms. These are release targets, not measured results; any justified adjustment must be documented with the owner rather than silently weakening the gate.
- **Sustained-use and regression checks:** run at least a two-hour mixed-work session and 20 repeated viewer/navigation/playback open-close cycles. After warm-up, compare equivalent idle checkpoints for retained memory, handles/listeners and child processes; unexplained continued growth blocks sign-off. Repeat the previously failing scenario and the combined workload after repairs, preserving local edits/outbox and verifying final sync counts. Record PASS/FAIL/BLOCKED/NOT RUN, reproduction steps, traces, before/after measurements and remaining limitations in WORK_LOG.
